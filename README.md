#  Mini NPU Simulator — MAC 연산으로 Cross / X 판별하기

컴퓨터가 '모양'을 숫자로만 인식한다는 점에서 출발해, **MAC(Multiply-Accumulate)** 연산으로
N×N 패턴이 십자가(Cross)인지 X인지 판별하는 콘솔 시뮬레이터. NumPy 없이 **표준 라이브러리 + 반복문**으로만
MAC을 직접 구현하고, 크기별 연산 시간을 측정해 **O(N²)** 성장을 눈으로 확인한다.

- **저장소:** `https://github.com/SSUNOWL/codyssey-week1-mini-npu-simulator` · 제출 브랜치: **`main`**
- **실행:** `python main.py` (Python 3.8 이상, 외부 라이브러리 없음)

---

## 1. 미션 개요

NPU가 하는 핵심 연산인 MAC(같은 위치끼리 곱해서 전부 더하기)을 코드로 재현한다. 두 개의 필터(Cross, X)에
입력 패턴을 각각 MAC 하면 두 개의 "유사도 점수"가 나오고, 더 높은 쪽이 그 패턴의 정체다. 3×3 직접 입력(모드1)과
`data.json` 일괄 분석(모드2)을 제공하며, 부동소수점 오차·라벨 표기 불일치·크기 불일치 같은 실전 문제를 처리한다.

## 2. 미션 주제 / 선택 이유
해당 없음 — 주제(MAC 연산)가 미션에서 고정으로 주어졌다.

| 키 | 값 | 의미 |

### 6-3. 핵심 개념 메모

- **MAC(Multiply-Accumulate)**: 두 배열을 겹쳐 같은 위치의 수를 곱하고(Multiply) 전부 더한다(Accumulate).
  결과가 클수록 필터와 패턴이 "닮았다". AI의 합성곱/행렬곱이 전부 이 연산의 반복이라 NPU가 이를 **병렬**로 처리한다.
- **왜 NPU인가**: 3×3은 곱셈 9번이지만 25×25는 625번, 실제 모델은 수억 번이다. CPU의 직렬 처리로는 느려서
  수천 개 MAC을 동시에 처리하는 전용 칩(NPU)이 필요하다.
- **라벨 정규화**: 같은 개념을 `+`/`cross`/`x` 처럼 다르게 적어 두면 비교가 깨진다. 내부에서 `Cross`/`X`
  **표준 라벨**로 통일해야 expected와 필터 라벨을 한 기준으로 비교(PASS/FAIL)할 수 있다.
- **부동소수점 & epsilon**: `0.1` 같은 실수는 이진 표현이 정확하지 않아 `0.9 vs 0.8999999999999999`처럼
  미세 오차가 난다. 이 오차로 대소가 뒤집히면 판정이 요동친다. 그래서 `|a-b| < 1e-9` 이면 **동점(UNDECIDED)**으로 처리한다.
- **O(N²)**: MAC은 N×N 칸을 모두 훑으므로 연산 횟수가 정확히 `N²`. 패턴이 커지면 시간이 제곱으로 늘어난다.

### 6-4. 설계 결정 (Why)

| 결정 | 선택한 방식 | 왜(근거) | 버린 대안 |
|------|-------------|----------|-----------|
| 데이터 구조 | `Matrix` 클래스(`get/set/size/to_flat` + 정사각 검증) | 요구사항의 "위치별 저장·조회"를 한 곳에 캡슐화하고, 비정사각 입력을 생성 시점에 걸러 낸다 | 생 2차원 리스트(검증이 곳곳에 흩어짐) / `dict[(r,c)]`(N×N 밀집 배열엔 과함) |
| 점수 비교 | epsilon `abs(a-b) < 1e-9` → 동점 UNDECIDED | `0.1` 등의 이진 부동소수점 오차(1e-16 수준)로 대소가 뒤집혀 판정이 흔들리는 것을 막는다 | 단순 `>` 비교(노이즈에 요동) / `round()` 비교(자릿수 선택이 임의적) / `Decimal`(느리고 미션 취지에서 벗어남) |
| 라벨 처리 | 입력을 표준 라벨 `Cross`/`X`로 **정규화 후** 비교 | `+`·`cross`·`x` 표기가 섞여 있어 한 기준으로 모아야 PASS/FAIL 비교가 일관됨 | 출력·비교 지점마다 조건 분기(중복·누락 실수 유발) |
| 모드2 오류 처리 | 케이스별 `try/except`로 격리, 필터 로드도 예상 예외를 전파하지 않음 | "스키마/크기 불일치에도 중단 금지" 요구 → 나쁜 케이스만 FAIL로 넘기고 요약까지 도달 | 사전 일괄 검증 후 중단(요구 위반) / 예외 전파(프로그램 크래시) |
| 성능 측정 패턴 | `generate_cross/x(N)`로 크기별 패턴·필터를 만들어 측정 | 3×3은 `data.json`에 없고, 크기별 N² 비교는 동일 방식으로 만든 입력이라야 공정 | `data.json` 패턴 재사용(3×3 부재·크기 커버 불완전) |
| 시간 측정 | `time.perf_counter` 10회 평균, 연산 구간만 | 고해상도 단조 시계로 I/O를 뺀 순수 MAC 시간을 잰다 | `time.time()`(해상도·되감김 문제) / 1회 측정(노이즈 큼) |
| 콘솔 인코딩 | 시작 시 `stdout/stdin`을 UTF-8로 `reconfigure` | Windows cp949 콘솔에서 `✓`·`×` 출력 시 크래시 방지 | 기호를 ASCII로 대체(예시 출력 가독성 저하) |

### 6-5. 예상 질의응답 (방어 노트)

- **Q. 실패 3건은 버그 아닌가요?** — A. 아닙니다. 세 케이스는 **정확한 십진 계산으로는 Cross·X 점수가 같은(차이 0) 동점** 입력입니다.
  부동소수점으로 계산하면 `1e-16`~`1e-15`의 미세 차만 남는데, epsilon이 이를 동점(UNDECIDED)으로 처리합니다.
  데이터 자체가 애매한(두 필터에 똑같이 반응하는) 입력이라는 걸 **정직하게 드러낸** 결과입니다.
- **Q. epsilon을 안 쓰면 어떻게 되나요?** — A. `size_5_1`은 Cross `0.9`, X `0.8999999999999999`처럼 차이가 `1e-16`에 불과한데,
  단순 `>` 비교면 이 표현오차만으로 Cross/X가 갈립니다(연산 순서·플랫폼이 바뀌면 어느 쪽이 커질지도 달라질 수 있습니다).
  epsilon은 이 정도 차이를 **동점으로 못박아** 판정이 float 잡음이 아니라 실제 점수 차에 근거하게 합니다.
- **Q. 왜 NumPy를 안 썼나요?** — A. 미션 제약(외부 라이브러리 금지)이자, MAC을 이중 `for`로 직접 써야 연산 횟수 `N²`와
  O(N²) 증가를 몸으로 확인할 수 있기 때문입니다.
- **Q. 1D(평탄화) 최적화가 왜 더 빠르지 않았나요?** — A. 실행하면 `bonus_compare_1d_2d`가 두 방식의 시간을 출력하는데,
  순수 파이썬에서는 차이가 크지 않았습니다(둘 다 같은 곱·합이고, 파이썬 객체 접근 비용이 지배). 1D 연속 접근의 이점은
  캐시·SIMD가 작동하는 저수준/하드웨어에서 커진다는 것이 일반적 설명이며, 이 미션이 NPU를 소개하는 맥락과 이어집니다.
  (수치는 실행해서 직접 보여줄 수 있습니다.)
- **Q. 잘못된 키·크기 불일치·깨진 JSON이 들어오면요?** — A. 두 층위로 나눠 처리합니다.
  ① **케이스 내부**의 스키마·키·크기·타입 오류는 케이스 단위 `try/except`로 해당 케이스만 FAIL로 남기고 **요약까지 진행**합니다
  (필터 로드 실패도 격리). ② **파일 전체**가 깨진 JSON이거나 최상위 구조가 객체가 아니면 트레이스백 없이 **안내 후 종료**합니다
  (이 경우 요약은 없음). 어느 쪽도 파이썬 트레이스백으로 비정상 종료되지는 않습니다.
- **Q. 모드1은 A/B, 모드2는 Cross/X로 판정이 다른 이유는?** — A. 모드1은 사용자가 넣은 **임의의 필터 2개**라 이름을 A/B로,
  모드2는 `data.json`의 정규화된 **Cross·X 필터**라 표준 라벨로 판정합니다. 판정 로직(`judge`)은 동일합니다.

## 결과 리포트 (실패 원인 분석 + 시간 복잡도 분석)

**집계:** 총 6 케이스 → **통과 3 / 실패 3**. 실패 케이스: `size_5_1`, `size_13_2`, `size_25_1` (모두 동점 UNDECIDED).

**실패 원인 분석 — "데이터/스키마 vs 로직 vs 수치 비교"로 분리:**
- 세 실패는 **스키마 오류가 아니다**(모든 키·크기가 정상 로드됨). **로직 버그도 아니다**(정규화·판정 규칙 정상).
  원인은 **수치 비교** 영역이다. 세 패턴은 Cross 필터 점수와 X 필터 점수가 **수학적으로 동점**이 되도록 설계되었다.
- 실제 차이를 보면 `size_5_1`은 `0.9`와 `0.8999999999999999`(차이 ≈ `1.1e-16`), `size_13_2`는 `7.499999999999997`와 `7.5`
  (차이 ≈ `2.7e-15`), `size_25_1`은 `4.9`와 `4.899999999999999`(차이 ≈ `1.8e-15`)이다. 이는 `0.1`·`0.3` 같은 실수를
  이진 부동소수점으로 저장할 때 생기는 **표현 오차**다.
- epsilon(`1e-9`)이 **없다면** 이 1e-16 수준의 노이즈로 대소가 뒤집혀 판정이 무작위로 흔들린다. epsilon을 적용하면
  "사실상 같은 점수"를 정직하게 **UNDECIDED**로 처리하고, expected와 다르므로 **FAIL**로 남긴다. 즉 이 FAIL은
  **버그가 아니라 "판별 불가한 애매한 입력"을 안전하게 드러낸 결과**다. (통과 3건은 점수 차가 커서 흔들림이 없다.)

**시간 복잡도 분석 — O(N²) 근거:**
- MAC은 N×N 칸을 한 번씩 곱·합하므로 연산 횟수가 정확히 `N²`이다(표의 "연산 횟수" 열 = 9, 25, 169, 625).
- 측정(10회 평균) 예시: 3×3 ≈ 0.001 ms, 5×5 ≈ 0.0015 ms, 13×13 ≈ 0.006 ms, 25×25 ≈ 0.019 ms.
  작은 N에서는 함수 호출·루프 준비 같은 **고정 비용**이 커서 시간이 N²에 정확히 비례하진 않지만, N이 커질수록
  `N²` 항이 지배해 25×25가 13×13의 약 3~4배(면적비 625/169 ≈ 3.7)로 늘어난다. → **연산량·시간 모두 O(N²)**.
- (보너스) 2D를 1D로 평탄화해도 순수 파이썬에서는 인덱싱 오버헤드가 비슷해 뚜렷한 이득이 없었다. 1D 최적화는
  캐시·SIMD가 작동하는 저수준/하드웨어(NPU)에서 의미가 커진다 — 이 미션이 NPU의 존재 이유를 설명하는 지점이다.

## 10. 트러블슈팅 (2건 이상)

### 1) Windows 콘솔에서 `UnicodeEncodeError: 'cp949'` (✓·× 출력 실패)
- **원인:** 기본 콘솔 인코딩이 cp949라 `✓`(U+2713) 등 유니코드 기호를 인코딩하지 못함.
- **해결:** 시작 시 `sys.stdout/stdin.reconfigure(encoding="utf-8")` 로 UTF-8 고정(3.7+). 실패 시 조용히 무시.

### 2) 동점인데 판정이 실행마다 달라짐(부동소수점)
- **원인:** `0.9`와 `0.8999999999999999`를 단순 `>` 로 비교하면 미세 오차로 대소가 뒤집힘.
- **해결:** `abs(a-b) < 1e-9` 이면 UNDECIDED. 노이즈에 흔들리지 않고 재현성 있는 판정.

## 11. 보너스 과제 (전부 구현)

### (1) 시뮬레이터 최적화 — 2D → 1D 평탄화
`Matrix.to_flat()` 로 N×N 을 길이 N² 1차원 리스트로 변환하고 `mac_1d()` 로 계산. `bonus_compare_1d_2d(25)` 가
동일 입력·동일 10회 반복으로 2D와 1D 시간을 비교 출력한다. (결과 해석은 위 "결과 리포트" 참조.)

### (2) 패턴 생성기
`generate_cross(N)`(가운데 행·열=1), `generate_x(N)`(두 대각선=1)로 임의 크기 Cross/X 패턴을 자동 생성한다.
성능 분석 표(3/5/13/25)가 이 생성기를 재활용해 각 크기의 패턴·필터를 만들어 시간을 측정한다.
