#  Mini NPU Simulator — MAC 연산으로 Cross / X 판별하기

컴퓨터가 '모양'을 숫자로만 인식한다는 점에서 출발해, **MAC(Multiply-Accumulate)** 연산으로
N×N 패턴이 십자가(Cross)인지 X인지 판별하는 콘솔 시뮬레이터. NumPy 없이 **표준 라이브러리 + 반복문**으로만
MAC을 직접 구현하고, 크기별 연산 시간을 측정해 **O(N²)** 성장을 눈으로 확인한다.

한눈에 보는 결과

data.json 6개 케이스 중 3개가 PASS, 3개가 FAIL이다. 실패 3건은 버그가 아니라 데이터가 크기별로 하나씩 심어 둔 동점 케이스로,
Cross 필터 점수와 X 필터 점수가 수학적으로 정확히 같도록 필터 값이 설계되어 있다(0.9 = 0.1×9, 7.5 = 0.3×25, 4.9 = 0.1×49).
부동소수점으로 계산하면 1~3 ULP(1e-16~1e-15) 수준의 차이만 남는데, epsilon 1e-9 정책이 이를 동점(UNDECIDED)으로 처리해 FAIL로 집계한다.
즉 판별할 수 없는 입력을 임의로 찍지 않고 그대로 드러내는 것이 이 결과이며, 근거는 아래 "결과 리포트"에 정리했다.

### 6-3. 핵심 개념 메모

- **MAC(Multiply-Accumulate)**: 두 배열을 겹쳐 같은 위치의 수를 곱하고(Multiply) 전부 더한다(Accumulate).
  결과가 클수록 필터와 패턴이 "닮았다". AI의 합성곱/행렬곱이 전부 이 연산의 반복이라 NPU가 이를 **병렬**로 처리한다.
- **왜 NPU인가**: 3×3은 곱셈 9번이지만 25×25는 625번, 실제 모델은 수억 번이다. 이런 단순 반복을 범용 CPU로 감당하기 어려워
  MAC을 대량으로 처리하는 전용 칩(NPU)이 나왔다. 셋의 차이는 아래 6-3-1에 따로 정리했다.
- **라벨 정규화**: 같은 개념을 `+`/`cross`/`x` 처럼 다르게 적어 두면 비교가 깨진다. 내부에서 `Cross`/`X`
  **표준 라벨**로 통일해야 expected와 필터 라벨을 한 기준으로 비교(PASS/FAIL)할 수 있다.
- **부동소수점 & epsilon**: `0.1` 같은 실수는 이진 표현이 정확하지 않아 `0.9 vs 0.8999999999999999`처럼
  미세 오차가 난다. 이 오차로 대소가 뒤집히면 판정이 요동친다. 그래서 `|a-b| < 1e-9` 이면 **동점(UNDECIDED)**으로 처리한다.
- **O(N²)**: MAC은 N×N 칸을 모두 훑으므로 연산 횟수가 정확히 `N²`. 패턴이 커지면 시간이 제곱으로 늘어난다.
- **점수는 절대 기준이 아니라 상대 기준이다**: MAC 점수 자체에는 "몇 점 이상이면 Cross" 같은 절대 의미가 없다.
  필터 값의 스케일에 따라 얼마든지 커지거나 작아지기 때문이다(예: `size_25_2`는 52.9, `size_5_2`는 8.9인데 둘 다 같은 Cross 판정이다).
  의미가 있는 것은 두 필터 점수의 **대소 관계**뿐이며, 이 프로그램도 임계값이 아니라 Cross 점수와 X 점수의 비교로만 판정한다.

#### 6-3-1. CPU · GPU · NPU는 무엇이 다른가

셋의 차이는 성능 수치가 아니라 어떤 작업이 올 것이라고 가정하고 만들었는가에서 나온다.

CPU는 무엇이 올지 모른다고 가정한다. 그래서 모든 연산 결과가 레지스터에 들어가고, 그 값을 다음에 무엇에든 쓸 수 있게 해 둔다.
방금 계산한 값으로 조건을 판단할 수도, 메모리에 저장할 수도, 다른 연산에 넘길 수도 있다. 레지스터가 모든 명령이 들여다보는 공용 게시판 역할을 하는 셈이다.
제어 흐름이 복잡한 코드에 강한 이유가 여기 있다. 게다가 CPU는 분기 결과를 기다리지 않고 미리 예측해서 실행해 두었다가, 틀리면 그동안 한 일을 되돌린다.
예측하고 되돌리고 명령들 사이의 의존 관계를 추적하는 이 장치들이 칩 면적과 전력의 상당 부분을 차지한다.
바꿔 말하면 CPU는 병렬 처리를 못 하는 것이 아니라, 임의의 코드에서 병렬성을 알아서 찾아내느라 값비싼 장치를 잔뜩 달고 있는 구조다.

GPU는 같은 코드를 서로 다른 데이터에 대량으로 적용한다고 가정한다. 핵심은 제어 로직을 여러 연산 유닛이 나눠 쓰는 것이다.
스레드를 수십 개씩 묶어 실행하는데 그 묶음은 명령을 하나만 쓴다. 명령을 읽고 해석하는 일을 한 번만 하고 여러 유닛이 각자의 데이터로 동시에 계산하므로,
유닛 하나당 제어 비용이 크게 줄고 같은 면적에 연산 유닛을 훨씬 많이 넣을 수 있다.
여기서 말하는 병렬은 보통 하나의 큰 작업을 같은 모양의 조각으로 잘게 나눈 것이다.
이미지의 모든 픽셀을 밝게 만드는 일처럼, 조각끼리 서로 영향을 주지 않고 코드가 동일하면 GPU에 맞는 작업이 된다.
약점도 같은 구조에서 나온다. 한 묶음 안에서 조건문이 갈리면 명령이 하나뿐이라 양쪽을 차례로 다 실행하고 해당 없는 쪽 결과를 버려야 하므로, 분기가 많으면 효율이 떨어진다.
메모리를 기다리는 방식도 CPU와 반대다. CPU가 큰 캐시로 기다리는 시간 자체를 줄인다면, GPU는 한 묶음이 대기에 들어가면 즉시 다른 묶음으로 갈아타 기다림을 다른 일로 덮는다.
그래서 GPU는 대기 중인 작업이 넘칠 만큼 많아야 제 성능이 난다.

NPU는 한 걸음 더 나가서 신경망의 특정 연산만 온다고 가정한다. 그래서 데이터가 흘러갈 경로 자체를 하드웨어에 고정한다.
CPU와 GPU가 계산할 때마다 레지스터에서 값을 읽고 결과를 다시 쓰는 것과 달리, NPU의 연산 배열은 계산 유닛끼리 값을 직접 넘긴다.
중간 결과가 옆 칸으로 흘러가며 계산이 이어지므로 계산 하나당 데이터를 옮기는 거리가 짧아지고, 이것이 전력 효율 차이의 대부분을 만든다.
가중치를 칩 안에 상주시켜 매번 불러오지 않는 것, 어떤 데이터를 언제 올릴지 컴파일러가 미리 정해 두는 것도 같은 목적이다.
대가는 유연성이다. 지원하지 않는 연산이 모델에 섞여 있으면 그 부분은 다시 CPU가 맡아야 한다.

이 미션의 관점에서 중요한 점은, NPU의 본질이 곱셈기를 많이 깐 것이 아니라 데이터 이동을 줄인 것이라는 사실이다.
계산 유닛만 늘리면 그 유닛들을 먹일 데이터가 따라오지 못해 대부분이 값을 기다리며 놀게 된다.
그래서 이 과제에서는 NPU가 어울리지 않는다. 이유는 두 가지인데 성격이 다르다.
하나는 작업이 너무 작아서 가속기에 보내고 준비하는 시간이 계산보다 오래 걸린다는 점이고, 이것은 크기를 키우면 사라진다.
다른 하나는 이 연산이 필터와 패턴을 한 번씩만 곱해 데이터를 재사용하지 않는다는 점이고, 이것은 크기를 키워도 사라지지 않는다.
NPU가 제 성능을 내려면 크기가 아니라 연산의 성격이 달라져야 한다. 합성곱처럼 같은 필터를 수많은 위치에 다시 쓰는 구조라야
한 번 올린 데이터로 계산을 계속 이어 갈 수 있고, 그제야 깔아 둔 유닛들이 모두 일하게 된다.

### 6-4. 설계 결정 (Why)

| 결정 | 선택한 방식 | 왜(근거) | 버린 대안 |
|------|-------------|----------|-----------|
| 데이터 구조 | `Matrix` 클래스(`get/set/size/to_flat` + 정사각 검증) | 요구사항의 "위치별 저장·조회"를 한 곳에 캡슐화하고, 비정사각 입력을 생성 시점에 걸러 낸다 | 생 2차원 리스트(검증이 곳곳에 흩어짐) / `dict[(r,c)]`(N×N 밀집 배열엔 과함) |
| 점수 비교 | epsilon `abs(a-b) < 1e-9` → 동점 UNDECIDED | `0.1` 등의 이진 부동소수점 오차(1e-16 수준)로 대소가 뒤집혀 판정이 흔들리는 것을 막는다 | 단순 `>` 비교(노이즈에 요동) / `round()` 비교(자릿수 선택이 임의적) / `Decimal`(느리고 미션 취지에서 벗어남) |
| 라벨 처리 | 입력을 표준 라벨 `Cross`/`X`로 **정규화 후** 비교 | `+`·`cross`·`x` 표기가 섞여 있어 한 기준으로 모아야 PASS/FAIL 비교가 일관됨 | 출력·비교 지점마다 조건 분기(중복·누락 실수 유발) |
| 모드2 오류 처리 | 케이스별 `try/except`로 격리, 필터 로드도 예상 예외를 전파하지 않음 | "스키마/크기 불일치에도 중단 금지" 요구 → 나쁜 케이스만 FAIL로 넘기고 요약까지 도달 | 사전 일괄 검증 후 중단(요구 위반) / 예외 전파(프로그램 크래시) |
| 성능 측정 패턴 | `generate_cross/x(N)`로 크기별 패턴·필터를 만들어 측정 | 3×3은 `data.json`에 없고, 크기별 N² 비교는 동일 방식으로 만든 입력이라야 공정 | `data.json` 패턴 재사용(3×3 부재·크기 커버 불완전) |
| 시간 측정 | `time.perf_counter` 10회 평균, 연산 구간만 | 고해상도 단조 시계로 I/O를 뺀 순수 MAC 시간을 잰다 | `time.time()`(해상도·되감김 문제) / 1회 측정(노이즈 큼) |
| 콘솔 인코딩 | 시작 시 `stdout/stdin`을 UTF-8로 `reconfigure` | Windows cp949 콘솔에서 `✓`·`×` 출력 시 크래시 방지 | 기호를 ASCII로 대체(예시 출력 가독성 저하) |

### 6-5. 오류 처리 정책 (2층 방어)

모드2는 잘못된 입력을 **두 층위로 나눠** 처리한다.
- **케이스 내부** — 스키마·키·크기·타입 오류는 케이스 단위 `try/except`로 격리해 해당 케이스만 FAIL로 남기고
  **결과 요약까지 진행**한다(필터 로드 실패도 같은 방식으로 격리).
- **파일 전체** — 깨진 JSON이거나 최상위 구조가 객체가 아니면 트레이스백 없이 **안내 후 종료**한다(이 경우 요약은 없음).

어느 쪽도 파이썬 트레이스백으로 비정상 종료되지 않는다. 자주 나오는 두 상황의 처리 방침은 다음과 같다.

| 상황 | 처리 | 왜 이렇게 했나 |
|------|------|----------------|
| 패턴 키 크기에 맞는 필터가 없음 (예: `size_9_1`인데 `size_9` 필터가 없음) | 해당 케이스만 `FAIL (데이터/스키마 오류: size_9 필터가 없습니다)` 로 남기고 나머지는 계속 진행 | 명세가 "불일치 시 케이스 FAIL + 원인 메시지"를 요구한다. 생성기로 대체 필터를 만들어 채우면 없는 데이터를 지어내는 셈이라 채택하지 않았다 |
| 키 형식이 규칙과 다름 (예: `weird_key`) | 정렬에서 뒤로 밀되 크래시 없이 케이스 FAIL 처리 | 스키마를 신뢰할 수 없는 입력에서도 요약까지 도달해야 하므로, 추측으로 복구하지 않고 실패로 명시한다 |

### 6-6. 모드별 동점 처리 비교

같은 `judge()` 함수를 쓰지만 라벨과 집계 방식이 다르다.

| 구분 | 모드1 (사용자 입력) | 모드2 (data.json) |
|------|---------------------|-------------------|
| 비교 대상 | 사용자가 넣은 임의의 필터 A, B | 정규화된 Cross, X 필터 |
| 동점일 때 출력 | `판정: 판정 불가 (\|A-B\| = 0.000e+00 < EPS 1e-09)` | `판정: UNDECIDED \| expected: X \| FAIL (동점 규칙)` |
| 집계 | 없음(단일 실행) | FAIL로 집계하고 실패 사유에 실제 점수 차를 남김 |
| 이유 | 정답(expected)이 없으므로 알리기만 한다 | expected와 대조해야 하므로 판정 불가는 불일치로 처리한다 |

## 결과 리포트 (실패 원인 분석 + 시간 복잡도 분석)

**집계:** 총 6 케이스 → **통과 3 / 실패 3**. 실패 케이스: `size_5_1`, `size_13_2`, `size_25_1` (모두 동점 UNDECIDED).

**실패 원인 분석 — "데이터/스키마 vs 로직 vs 수치 비교"로 분리:**
- 세 실패는 **스키마 오류가 아니다**(모든 키·크기가 정상 로드됨). **로직 버그도 아니다**(정규화·판정 규칙 정상).
  원인은 **수치 비교** 영역이다. 세 패턴은 Cross 필터 점수와 X 필터 점수가 **수학적으로 동점**이 되도록 설계되었다.
- 실제 차이를 보면 `size_5_1`은 `0.9`와 `0.8999999999999999`(차이 ≈ `1.1e-16`), `size_13_2`는 `7.499999999999997`와 `7.5`
  (차이 ≈ `2.7e-15`), `size_25_1`은 `4.9`와 `4.899999999999999`(차이 ≈ `1.8e-15`)이다. 이는 `0.1`·`0.3` 같은 실수를
  이진 부동소수점으로 저장할 때 생기는 **표현 오차**다.
- epsilon(`1e-9`)이 **없다면** 이 1e-16 수준의 노이즈로 대소가 뒤집혀 판정이 무작위로 흔들린다. epsilon을 적용하면
  "사실상 같은 점수"를 정직하게 **UNDECIDED**로 처리하고, expected와 다르므로 **FAIL**로 남긴다. 즉 이 FAIL은
  **버그가 아니라 "판별 불가한 애매한 입력"을 안전하게 드러낸 결과**다. (통과 3건은 점수 차가 커서 흔들림이 없다.)

### 상세 분석 1 — 점수가 왜 그 값으로 나왔는가

data.json의 필터는 모든 칸이 같은 값이 아니다. 0이 아닌 칸만 정리하면 다음과 같다.

| 필터 | 0이 아닌 칸 | 값 구성 |
|------|-------------|---------|
| size_5 cross | 십자 9칸 | 1.0 × 8 + 중앙 0.9 |
| size_5 x | 대각선 9칸 | 0.1 × 9 |
| size_13 cross | 십자 25칸 | 0.3 × 25 |
| size_13 x | 대각선 25칸 | 0.3 × 24 + 중앙 7.5 |
| size_25 cross | 십자 49칸 | 1.0 × 48 + 중앙 4.9 |
| size_25 x | 대각선 49칸 | 0.1 × 49 |

패턴은 0과 1로만 되어 있다. Cross 패턴은 십자 2N-1칸이 1이고, X 패턴은 대각선 2N-1칸이 1이다.
N이 홀수이므로 십자와 대각선은 정확히 중앙 한 칸에서만 만난다. 따라서 겹치는 칸 수는 두 가지뿐이다.
같은 모양끼리 겹치면 2N-1칸 전부, 다른 모양끼리 겹치면 중앙 1칸이다.
패턴 값이 0/1이므로 MAC 점수는 곧 "겹친 칸의 필터 값 합"이 된다. 케이스별로 풀어 쓰면 다음과 같다.

| 케이스 | 패턴 | Cross 점수 | X 점수 | 결과 |
|--------|------|-----------|--------|------|
| size_5_1 | X | 중앙 0.9 = 0.9 | 0.1 × 9 = 0.9 | 동점 |
| size_5_2 | Cross | 1.0 × 8 + 0.9 = 8.9 | 중앙 0.1 = 0.1 | 차이 8.8 |
| size_13_1 | X | 중앙 0.3 = 0.3 | 0.3 × 24 + 7.5 = 14.7 | 차이 14.4 |
| size_13_2 | Cross | 0.3 × 25 = 7.5 | 중앙 7.5 = 7.5 | 동점 |
| size_25_1 | X | 중앙 4.9 = 4.9 | 0.1 × 49 = 4.9 | 동점 |
| size_25_2 | Cross | 1.0 × 48 + 4.9 = 52.9 | 중앙 0.1 = 0.1 | 차이 52.8 |

여기서 데이터의 설계 의도가 드러난다. 각 크기마다 한쪽 필터의 중앙값이 반대쪽 필터 전체 합과 같도록 맞춰져 있다.
0.9 = 0.1 × 9, 7.5 = 0.3 × 25, 4.9 = 0.1 × 49 이다.
즉 실패 3건은 데이터가 크기별로 하나씩 심어 둔 동점 함정이고, 통과 3건은 점수 차가 8.8 이상이라 어떤 오차에도 흔들리지 않는다.

### 상세 분석 2 — 부동소수점 오차의 크기와 epsilon 값의 근거

정확한 십진 계산으로는 위 세 쌍이 완전히 같지만, 실행하면 0.9와 0.8999999999999999처럼 미세하게 다르다.
왜 그런지 알려면 컴퓨터가 실수를 어떻게 저장하는지부터 봐야 한다.

#### 컴퓨터가 실수를 저장하는 방식 (IEEE 754)

파이썬의 float은 C의 double과 같은 IEEE 754 배정밀도(binary64)다. 64비트를 세 부분으로 나눠 쓴다.

| 형식 | 전체 | 부호 s | 지수 e | 가수 f | 십진 유효자리 |
|------|------|--------|--------|--------|----------------|
| binary32 (C의 float) | 32비트 | 1비트 | 8비트 (바이어스 127) | 23비트 | 약 7자리 |
| binary64 (C의 double, 파이썬 float) | 64비트 | 1비트 | 11비트 (바이어스 1023) | 52비트 | 약 15~17자리 |

정규화된 수의 값은 다음 식으로 정해진다(binary64 기준).

값 = (-1)^s × (1 + f / 2^52) × 2^(e - 1023)

즉 컴퓨터는 실수를 2진수로 바꾼 뒤 소수점 앞이 1이 되도록 자리를 옮기고(1.xxxx 형태), 옮긴 만큼을 2의 거듭제곱 지수로 기록한다.
10진 과학적 표기법 1.23 × 10^4의 2진 버전이라고 보면 된다. 여기서 가수 f가 52비트뿐이므로 1.xxxx의 소수부는 52자리에서 잘리고 반올림된다.

위 식은 정규화된 수에 대한 것이다. 지수가 표현 가능한 최솟값 아래로 내려가는 0 근처의 아주 작은 수는
서브노멀(비정규화 수)로 저장되어 앞의 1이 붙지 않고 유효자리도 줄어든다. 이 미션에서 다루는 값(0.1~52.9)은 전부 정규화 구간이라
아래 분석에 영향을 주지 않지만, 식이 모든 실수에 그대로 적용되는 것은 아니라는 점은 알아 둘 필요가 있다.

핵심 규칙은 이것이다. 기약분수 p/q가 2진 유한소수가 되려면 분모 q가 2의 거듭제곱이어야 한다.
0.5 = 1/2, 0.25 = 1/4, 7.5 = 15/2는 이 조건을 만족해 오차 없이 저장된다.
실제로 7.5의 비트 표현은 401E000000000000으로 가수 뒷부분이 전부 0이다.

#### 예시: 0.1은 왜 표현하지 못하는가

0.1 = 1/10 = 1/(2 × 5)이고 분모에 5가 남아 있어 2진 유한소수가 될 수 없다.
10진법에서 1/3을 0.333...으로밖에 쓸 수 없는 것과 정확히 같은 상황이며, 진법이 바뀌면서 걸리는 분모가 달라졌을 뿐이다.
소수부에 2를 곱해 정수부를 떼는 방식으로 직접 2진 전개를 해 보면 다음과 같다.

```
0.1 × 2 = 0.2 → 0
0.2 × 2 = 0.4 → 0
0.4 × 2 = 0.8 → 0
0.8 × 2 = 1.6 → 1   (0.6 남음)
0.6 × 2 = 1.2 → 1   (0.2 남음)
0.2 × 2 = 0.4 → 0   ← 앞의 0.2가 다시 나왔다. 여기서부터 순환
```

0.1 = 0.0001100110011001100...(2) 로 0011이 무한히 반복된다. 52비트에서 끊고 반올림해야 하므로
저장되는 값은 0.1 자체가 아니라 0.1에 가장 가까운 다른 수가 된다. 파이썬으로 0.1의 비트를 뜯어보면 다음과 같다.

| 항목 | 값 |
|------|-----|
| 부호 비트 | 0 (양수) |
| 지수 비트 | 01111111011 = 1019, 실지수는 1019 - 1023 = -4 |
| 가수 | 1.1001100110011001...(2) = 1.6 (이 1.6도 8/5이라 2진 순환소수다) |
| 조합 | 1.6 × 2^-4 = 0.1 로 보이지만, 1.6이 52비트에서 잘린 근사값이다 |
| 16진 표현 | 3FB999999999999A (끝자리 A는 잘린 부분을 반올림하며 올라간 흔적) |
| 실제 저장된 십진값 | 0.1000000000000000055511151231257827021181583404541015625 |
| 분수 표현 | 3602879701896397 / 2^55 |

즉 파이썬이 0.1이라고 보여 주는 값은 실제로는 0.1보다 약 5.55e-18 크다.
0.3도 마찬가지로 저장 시점에 약 1.11e-17 작아진다(3FD3333333333333).
반면 0.5나 7.5는 3FE0000000000000, 401E000000000000처럼 정확히 저장된다.

#### 한 번의 오차는 작지만 더할수록 쌓인다

MAC은 이 값을 계속 더한다. 0.1을 아홉 번 누적하는 과정을 그대로 찍어 보면 다음과 같다.

```
1회 0.1                 4회 0.4                 7회 0.7
2회 0.2                 5회 0.5                 8회 0.7999999999999999
3회 0.30000000000000004  6회 0.6                 9회 0.8999999999999999
```

세 번째에서 이미 오차가 보이고, 네 번째에서는 반올림이 반대 방향으로 작용해 다시 0.4로 돌아온다.
오차가 한 방향으로만 커지는 것이 아니라 누적과 상쇄를 반복한다는 뜻이다.
최종값 0.8999999999999999는 0.9 리터럴과 1 ULP 차이이며, 이것이 size_5_1의 X 점수다.
같은 방식으로 0.3을 25번 더하면 7.499999999999997(3 ULP 차, size_13_2의 Cross 점수),
0.1을 49번 더하면 4.899999999999999(2 ULP 차, size_25_1의 X 점수)가 된다.

여기서 같은 1 ULP인데도 절대 차이가 케이스마다 다른 이유도 설명된다.
ULP(마지막 비트 한 칸의 크기)는 값이 속한 2의 거듭제곱 구간마다 달라진다.
0.9는 [0.5, 1) 구간이라 ULP = 2^-53 = 1.11e-16이고, 4.9와 7.5는 [4, 8) 구간이라 ULP = 2^-50 = 8.88e-16이다.
수가 커질수록 표현 간격이 넓어지고 절대 오차도 같이 커진다. 고정값 epsilon을 쓸 때는 이 점을 알고 있어야 하며,
점수 범위가 훨씬 커지는 문제에서는 고정 epsilon 대신 상대 오차 비교로 바꿔야 한다.

#### 오차 상한 계산

이제 오차의 크기를 식으로 묶을 수 있다. 저장 시점 반올림에 더해, 값을 k번 더하는 동안 반올림이 k-1번 누적된다.
순차 합의 오차 상한은 다음과 같다(u는 단위 반올림, u = 2^-53 ≈ 1.11e-16).

오차 ≤ (k - 1) × u × Σ|x_i|

세 실패 케이스에 대입하면 다음과 같다.

| 케이스 | 항 수 k | 합 S | 오차 상한 (k-1)·u·S | 실측 차 | ULP 환산 |
|--------|---------|------|---------------------|---------|----------|
| size_5_1 X 점수 | 9 | 0.9 | 8.0e-16 | 1.1e-16 | 1 ULP |
| size_13_2 Cross 점수 | 25 | 7.5 | 2.0e-14 | 2.7e-15 | 3 ULP |
| size_25_1 X 점수 | 49 | 4.9 | 2.6e-14 | 1.8e-15 | 2 ULP |

실측 오차는 모두 상한 안에 있고 크기는 1~3 ULP 수준이다. 여기서 epsilon을 어디에 두어야 하는지가 정해진다.
아래로는 잡아야 할 노이즈(최대 약 1e-14)보다 커야 하고, 위로는 살려야 할 실제 점수 차(가장 작은 것이 8.8)보다 작아야 한다.
실제로 EPS 값을 바꿔 가며 6케이스를 재판정해 보면 다음과 같았다.

| EPS | 판정 결과 |
|-----|-----------|
| 1e-16 | 동점 3건이 전부 대소로 갈림(size_5_1 → Cross, size_13_2 → X, size_25_1 → Cross). 표현 오차의 방향이 판정을 결정한다 |
| 1e-15 | size_5_1만 UNDECIDED, 나머지 2건은 여전히 갈림 |
| 1e-14 ~ 8.8 미만 | 1e-9과 완전히 동일한 판정(동점 3건 UNDECIDED, 나머지 3건 정상 판정) |

주의할 점은 epsilon을 없앤다고 실패가 줄지 않는다는 것이다. EPS를 1e-16으로 두면 세 케이스 모두 대소가 갈리지만
갈린 방향이 expected와 맞지 않아 여전히 3건 FAIL이고, 대신 "판별 불가"라는 정보가 사라져 근거 없는 판정이 정답처럼 보이게 된다.
epsilon의 값어치는 실패를 없애는 데 있는 것이 아니라, 실패의 성격을 "애매한 입력"으로 정확히 드러내는 데 있다.

즉 1e-9은 [1e-14, 8.8]이라는 넓은 안전 구간의 가운데를 고른 값이며, 이 데이터에서는 1e-12로 낮추거나 1e-6으로 올려도 결과가 같다.
반대로 1e-15 이하로 내리면 판정이 표현 오차에 좌우되기 시작한다.

### 상세 분석 3 — 시간 복잡도 계산 수식과 근사식

먼저 코드 구조에서 연산 횟수를 직접 센다. mac_2d는 바깥 루프 N회, 안쪽 루프 N회다.

- 곱셈: N²
- 덧셈(누적): N²
- 리스트 인덱싱: 2N² (패턴 1회 + 필터 1회)
- 행 참조: 2N (바깥 루프에서 prow, frow를 캐시)
- 부동소수점 연산 합계: 2N²

패턴 하나를 판정하려면 필터 2개와 MAC 하므로 2N²이고, data.json 6케이스 전체는
2 × (25 + 25 + 169 + 169 + 625 + 625) = 3276회의 곱셈과 같은 수의 덧셈이다.

실행 시간 모델은 다음과 같이 쓸 수 있다.

T(N) = c0 + c1·N + c2·N²

c0는 함수 호출과 지역변수 준비 같은 크기와 무관한 고정비, c1·N은 바깥 루프 1회당 비용(행 참조 2회와 루프 제어),
c2·N²는 원소당 비용(인덱싱 2회 + 곱 1회 + 누적 1회)이다. N이 커지면 c2·N² 항이 지배하므로 Θ(N²)이고, 상한으로 쓰면 O(N²)다.
c1·N 항은 N² 항에 비해 작아 아래 적합에서는 무시한다.

이 문서 작성 시점의 실측(모드2 성능표, 10회 평균)은 다음과 같다.

| 크기 | 평균 시간(ms) | 연산 횟수 N² | 원소당 비용 t/N² |
|------|---------------|--------------|------------------|
| 3×3 | 0.0009 | 9 | 약 100 ns |
| 5×5 | 0.0014 | 25 | 약 56 ns |
| 13×13 | 0.0059 | 169 | 약 35 ns |
| 25×25 | 0.0192 | 625 | 약 31 ns |

원소당 비용이 100 ns에서 31 ns로 떨어지다가 수렴하는 것이 고정비 c0의 흔적이다.
3×3에서는 전체 시간의 대부분이 고정비이고, 25×25에서는 N² 항이 지배한다.
양 끝 두 점(3×3, 25×25)으로 상수를 풀면 다음과 같다.

c2 = (0.0192 - 0.0009) / (625 - 9) = 2.97e-5 ms = 약 30 ns/원소
c0 = 0.0009 - 2.97e-5 × 9 = 0.00063 ms = 약 0.63 us

근사식: T(N) ≈ 0.00063 + 0.0000297 × N² (ms)

이 식으로 나머지 두 점을 예측하면 5×5는 0.00137 ms(실측 0.0014, 오차 -2%), 13×13은 0.00565 ms(실측 0.0059, 오차 -4%)로 잘 맞는다.
더 큰 크기로 외삽하면 51×51은 약 0.078 ms, 101×101은 약 0.30 ms인데, 실제로 재보면 이보다 20~40% 크게 나온다.
배열이 캐시에 다 들어가지 않기 시작하면서 원소당 비용 c2 자체가 조금 올라가기 때문이며, 차수(N²)가 틀린 것은 아니다.

비율로도 확인할 수 있다. N을 2배로 하면 이론상 시간은 4배가 되어야 한다.
13×13 → 25×25는 N² 비가 625/169 = 3.70인데 실측 비는 0.0192/0.0059 = 3.25로 근접한다.
반면 3×3 → 5×5는 N² 비 2.78에 실측 1.56으로 어긋나는데, 이는 O(N²)에 어긋나는 것이 아니라 작은 N에서 고정비 c0가 지배하기 때문이다.
근사식에 c0를 넣고 계산하면 이 어긋남까지 그대로 설명된다.

측정값을 읽을 때 주의할 점은 절대 시간이 실행 환경과 그 순간의 CPU 부하에 크게 흔들린다는 것이다.
같은 코드를 부하가 있는 상태에서 재측정했을 때 위 값의 2~3배까지 나왔다.
그래서 O(N²)의 근거로 삼는 것은 절대값이 아니라 원소당 비용의 수렴과 크기 사이의 비율이다.
원소당 비용은 프로그램 성능표의 "원소당(ns)" 열에 그대로 출력되므로 실행할 때마다 직접 확인할 수 있다.

큰 N에서의 예측 (시간과 메모리)

근사식을 그대로 외삽하면 다음과 같다. 이 미션의 요구 범위(최대 25×25)를 넘어서면 무엇이 먼저 문제가 되는지 가늠하는 용도다.

| 크기 | 연산 횟수 N² | 예측 시간 | 행렬 1개의 메모리(개략) |
|------|--------------|-----------|--------------------------|
| 25×25 | 625 | 0.019 ms | 7 KB(값 공유) ~ 21 KB(값이 모두 다름) |
| 100×100 | 10,000 | 0.30 ms | 85 KB ~ 319 KB |
| 1000×1000 | 1,000,000 | 약 30 ms | 8 MB ~ 32 MB |

메모리 추정은 파이썬 리스트가 값이 아니라 객체 포인터를 담기 때문에 두 가지로 갈린다.
0.0과 1.0만 쓰는 생성기 패턴은 같은 float 객체를 재사용해 포인터 배열(8바이트 × N²)만 늘어나 약 8 MB이고,
값이 전부 다르면 float 객체(24바이트)가 개별로 잡혀 약 32 MB가 된다. 필터와 패턴 두 개를 들면 이 값의 두 배다.
즉 1000×1000까지는 시간(30 ms)보다 메모리(수십 MB)가 먼저 체감되고, 그보다 커지면 시간이 제곱으로 늘어 병목이 뒤집힌다.

### 상세 분석 4 — 2D를 1D로 평탄화했을 때의 장단점과 이득 조건

무엇을 바꾸는 것인지부터 정리하면, 리스트의 리스트(rows[i][j])를 길이 N²의 리스트 하나로 펴고(to_flat)
이중 루프를 단일 루프로 바꾸는 것이다(mac_1d). 원소 (r, c)의 위치는 r × N + c로 계산한다.

장점

- 인덱스 구조가 단순해진다. 바깥 루프 N회분의 제어 비용과 행 참조 2N회가 사라지고 루프가 하나만 남는다.
- 메모리가 한 덩어리라 연속 접근이 된다. 저수준 언어에서는 캐시 라인 단위로 데이터가 딸려 오고, 하드웨어 프리페처가 다음 주소를 예측하기 쉽다.
- SIMD 벡터화와 타일링에 유리하다. 연속 버퍼여야 한 명령으로 4~16개 원소를 동시에 곱할 수 있다.
- GPU/NPU 커널이나 DMA 전송은 대부분 연속 버퍼를 요구하므로 변환 없이 그대로 넘길 수 있고, 직렬화·복사도 한 번에 끝난다.

단점

- 평탄화 자체가 N² 복사 비용이다. 측정해 보면 25×25에서 to_flat 1회가 MAC 1회의 약 20~30%였다(실행마다 변동). 매 호출마다 변환하면 손해다.
- 원본 2D를 유지한 채 1D 사본을 들면 메모리를 2배 쓴다.
- 가독성과 디버깅이 나빠진다. (r, c) 대신 r × N + c를 계산해야 하고 행 경계 정보가 사라져 off-by-one 실수가 나기 쉽다. 행 단위 교체나 슬라이싱도 불편하다.
- 순수 파이썬에서는 위 장점이 거의 실현되지 않는다(아래 측정 참고).

측정 결과와 해석

`bonus_compare_1d_2d()` 는 5×5·13×13·25×25에서 동일 입력·동일 반복(50회)으로 두 방식을 비교하고,
읽는 기준이 되는 두 값(이론 이득 1/N, 평탄화 비용)을 함께 출력한다. 실행 예는 다음과 같다.

```
크기       2D 평균/최소(ms)      1D 평균/최소(ms)      1D/2D  이론이득(1/N)  to_flat(ms)
5×5        0.0015 / 0.0014       0.0010 / 0.0009       0.64   20.0%          0.0004
13×13      0.0077 / 0.0064       0.0051 / 0.0049       0.67   7.7%           0.0021
25×25      0.0212 / 0.0200       0.0236 / 0.0218       1.11   4.0%           0.0065
```

측정된 차이(-36%, -33%, +11%)가 이론상 가능한 이득(20%, 7.7%, 4%)보다 크고 방향도 일정하지 않다.
이는 1D가 정말 빠르거나 느려서가 아니라 측정 노이즈가 효과보다 크다는 뜻이다. 원인을 세 가지로 나눠 확인했다.

첫째, 원소당 실행되는 바이트코드가 완전히 같다. 두 함수를 `dis` 로 뜯어 보면 안쪽 루프가 한 줄도 다르지 않다.

```
mac_2d 안쪽 루프          mac_1d 루프
FOR_ITER                  FOR_ITER
STORE_FAST  j             STORE_FAST  k
LOAD_FAST   score         LOAD_FAST   score
LOAD_FAST   prow          LOAD_FAST   flat_pattern
LOAD_FAST   j             LOAD_FAST   k
BINARY_SUBSCR             BINARY_SUBSCR
LOAD_FAST   frow          LOAD_FAST   flat_filter
LOAD_FAST   j             LOAD_FAST   k
BINARY_SUBSCR             BINARY_SUBSCR
BINARY_OP   *             BINARY_OP   *
BINARY_OP   +=            BINARY_OP   +=
STORE_FAST  score         STORE_FAST  score
```

원소당 하는 일이 같으므로 1D가 아낄 수 있는 것은 바깥 루프(N회)뿐이고, 그 몫은 전체의 약 1/N 이다.
실제로 바깥 루프만 따로 재 보면 25×25에서 전체의 5.1%, 101×101에서 1.3%로 이론값 1/N과 일치했다.

둘째, 프로그램 기본 반복 횟수로는 그 5%를 분해할 수 없다. 10회 평균으로 같은 비교를 15번 반복했더니
1D/2D 비율이 0.97~1.77(폭 79%)로 흔들렸다. 재려는 효과보다 노이즈가 15배 크므로 실행할 때마다 순위가 뒤집힌다.
보너스 비교의 반복 횟수를 50회로 올리고 평균과 함께 최소값을 출력하는 이유가 이것이다.

셋째, 1D는 오히려 추가 비용을 낸다. CPython은 -5~256 범위의 정수만 캐시해 재사용하는데,
`mac_1d` 의 인덱스 k는 N²-1까지 커져 그 범위를 넘어서면 반복마다 새 int 객체가 만들어진다.
`mac_2d` 의 안쪽 인덱스 j는 N-1까지만 커지므로 이 비용을 덜 낸다. 총 반복 횟수를 625로 맞추고 인덱스 크기만 바꿔 확인했다.

```
단일 루프(인덱스 0..624)   0.0205 ms
중첩 루프(인덱스 0..24)    0.0170 ms   ← 바깥 루프 25회를 더 도는데도 더 빠르다
range(625) 순회            0.0298 ms
미리 만든 정수 리스트 순회   0.0268 ms   ← 차이 11%가 인덱스 정수 객체 생성 비용
```

바깥 루프에서 아끼는 5%보다 인덱스 객체 생성에서 잃는 10~20%가 더 크다. 순수 파이썬에서 1D가 구조적으로 유리할 수 없는 이유다.

넷째(그리고 근본적으로), CPython의 list는 값이 아니라 객체 포인터의 배열이다. 평탄화해도 연속으로 놓이는 것은 포인터뿐이고
실제 float 객체는 힙에 흩어져 있어, 1D의 진짜 장점인 캐시 지역성과 SIMD가 애초에 실현되지 않는다.

참고로 평탄화 비용(`to_flat`)은 위 측정에 포함하지 않았다. 한 번 변환해 여러 번 쓴다고 가정했기 때문이다.
표의 마지막 열이 그 비용인데, 25×25에서 MAC 1회의 약 20~30%(패턴·필터 둘을 변환하면 그 두 배)에 해당한다.
매 호출마다 변환하는 구조라면 이 비용만으로 1D가 확실히 불리해진다.

어떤 경우에 이득인가

평탄화한 배열을 R번 재사용한다고 하면 이득 조건은 다음과 같이 쓸 수 있다.

R × (T_2d - T_1d) > C_flat, 여기서 C_flat은 평탄화 비용(N² 복사)

순수 파이썬에서는 T_2d - T_1d가 0 이하이므로 어떤 R에서도 조건이 성립하지 않는다.
반대로 C/C++/Rust, NumPy 내부 구현, GPU/NPU 커널처럼 값이 raw 배열로 연속 저장되는 환경에서는 T_2d - T_1d가 확실한 양수가 되며, 특히 다음 상황에서 이득이 커진다.

- 배열이 캐시보다 커서 메모리 접근이 병목일 때
- SIMD 명령으로 여러 원소를 한 번에 처리할 때
- 한 번 평탄화해 여러 번 재사용할 때(R이 커져 변환 비용이 상각될 때)
- 연산기(GPU/NPU)로 버퍼를 통째 전송해야 할 때

반대로 다음 상황에서는 2D를 그대로 두는 편이 낫다.

- 인터프리터 오버헤드가 지배하는 순수 파이썬
- 호출할 때마다 새로 변환해야 해서 R이 1에 가까울 때
- 행 단위 접근·수정이 잦고 코드 가독성이 더 중요할 때

정리하면 이 미션 범위(순수 파이썬)에서 1D 평탄화는 속도 최적화라기보다 자료 배치를 하드웨어 친화적인 형태로 바꾸는 연습에 가깝다.
실제 이득은 MAC을 병렬·벡터로 처리하는 층에서 나오며, 그것이 NPU가 따로 존재하는 이유와 같은 맥락이다.

큰 N을 다뤄야 한다면 어떤 순서로 손대야 하나

이 미션의 제약(외부 라이브러리 금지) 안에서는 아래 1~2번까지만 가능하고, 3번부터는 제약을 푸는 이야기다.
순서를 이렇게 잡는 이유는 앞 단계일수록 비용 대비 효과가 크고 코드 구조를 덜 흔들기 때문이다.

1. 불필요한 연산을 없앤다. 패턴이 0/1이면 0인 칸의 곱셈은 결과에 기여하지 않으므로 0이 아닌 위치만 순회하면 된다.
   이 데이터의 패턴은 2N-1칸만 1이라 N²이 아니라 O(N) 연산으로 줄어든다. 다만 이는 희소(sparse) 입력에서만 성립하는 최적화라
   일반 패턴에는 쓸 수 없고, 미션이 요구한 "N×N 전체를 훑는 MAC"의 취지와도 어긋나므로 본 구현에는 넣지 않았다.
2. 합산 구조를 바꾼다. 순차 합산 대신 쌍대(pairwise) 합산을 쓰면 오차 상한이 k가 아니라 log k에 비례해 정밀도가 크게 좋아진다.
   속도 이득은 없지만 큰 N에서 누적 오차가 문제가 될 때 첫 번째 대응책이다.
3. 메모리 배치를 바꾼다. 1D 평탄화 + 블록(타일) 단위 처리로 캐시에 들어가는 크기씩 나눠 계산한다.
   위에서 보았듯 이 이득은 값이 연속 저장되는 C 수준에서만 실현되므로, 파이썬이라면 `array` 모듈이나 확장 모듈로 내려가야 한다.
4. 병렬화한다. 행 단위로 나눠 여러 코어에 분배하거나(멀티프로세싱), GPU/NPU 커널로 넘긴다.
   MAC은 각 원소가 독립적이라 병렬화가 쉬운 대표적 연산이고, 이 지점이 NPU가 수천 개 MAC을 동시에 처리하는 이유와 정확히 맞닿는다.

### 상세 분석 5 — CPU와 NPU에서 병목이 각각 어디에 생기는가

같은 MAC 연산인데도 CPU에서 느려지는 이유와 NPU에서 느려지는 이유가 다르다. 원인을 따라가 보면 둘 다 한 가지 성질에서 갈라져 나온다.

이 과제의 MAC은 계산이 무거운 연산이 아니다. 원소 하나를 읽어 와서 한 번 곱하고 한 번 더한 뒤 버린다.
같은 값을 두 번 쓰는 일이 없으니, 옮겨 온 데이터에 비해 계산량이 아주 적다. 이런 연산을 두고 연산 강도가 낮다고 말한다.
합성곱은 같은 필터를 이미지의 모든 위치에 다시 쓰고 행렬곱은 각 원소를 여러 번 재사용하는 데 비해, 이 과제는 필터 하나와 패턴 하나를 딱 한 번 곱하고 끝난다.
그래서 이 연산의 성격은 "계산이 오래 걸리는 문제"가 아니라 "데이터를 나르는 문제"에 가깝고, 아래의 모든 병목이 여기서 파생된다.

파이썬 구현에서의 병목

안쪽 루프의 본문을 한 단계씩 늘려 가며 재 보면, 실제 곱셈과 덧셈이 차지하는 몫보다 값을 꺼내 오고 루프를 도는 몫이 훨씬 크다.
리스트에서 원소를 두 번 꺼내는 비용이 가장 크고, 루프를 한 칸 진행시키는 비용이 그다음이며, 정작 곱하고 더하는 일은 전체의 일부에 지나지 않는다.
여기에 파이썬 특유의 부담이 얹힌다. 명령 하나하나를 해석해서 실행하는 인터프리터 비용, 곱셈 결과가 나올 때마다 새 실수 객체를 만드는 비용,
그 객체들을 관리하는 참조 카운팅 비용이다. 같은 알고리즘을 C로 옮기면 이 층이 통째로 사라지므로 훨씬 빨라진다.

네이티브 CPU에서의 병목

인터프리터 층을 걷어내도 연산의 성질은 그대로다. 원소마다 값을 두 번 읽어 와서 곱셈과 덧셈을 한 번씩 하는데,
읽어 오는 횟수가 계산 횟수보다 많으니 계산기보다 메모리에서 값을 꺼내 오는 경로가 먼저 한계에 닿는다.
여기에 하나가 더 겹친다. 누적 변수는 직전 결과가 나와야 다음 덧셈을 시작할 수 있어서, 계산이 사슬처럼 줄지어 대기하게 된다.
그래서 실제로는 계산기가 놀면서 앞의 결과를 기다리는 시간이 생기고, 이를 풀려면 누적 변수를 여러 개로 나눠 동시에 진행시켜야 한다.
데이터가 캐시를 벗어날 만큼 커지면 그때부터는 메모리 대역폭이 상한이 된다.

NPU에서의 병목

NPU는 곱하고 더하는 유닛을 아주 많이 깔아 계산 능력을 끌어올린 하드웨어다. 그런데 계산 능력이 커진 만큼 그 유닛들을 먹일 데이터도 빨리 공급해야 한다.
이 과제처럼 재사용이 없는 연산은 원소를 한 번 쓰고 버리기 때문에, 유닛을 아무리 많이 깔아도 대부분이 값이 도착하기를 기다리며 놀게 된다.
계산기를 늘릴수록 노는 비율이 오히려 커지는 셈이다. NPU에서 병목이 메모리 쪽에 생긴다는 말은 이런 뜻이다.

이 과제 규모에서는 그보다 더 큰 문제가 있다. 전체 연산량 자체가 아주 작아서, 계산에 걸리는 시간보다
연산을 가속기로 보내고 결과를 돌려받는 준비 과정이 압도적으로 오래 걸린다. 커널을 띄우고 데이터를 옮기는 고정 비용이 계산 시간을 몇 자릿수 앞선다.
결국 3×3부터 25×25까지의 크기에서는 NPU에 보내는 순간 손해이고 CPU가 더 빠르다. NPU는 이런 크기의 문제를 위해 만들어진 것이 아니다.

그러면 NPU는 언제 이기는가

병목이 데이터 이동이므로, 이기는 방법은 계산기를 늘리는 것이 아니라 한 번 가져온 데이터를 더 많이 쓰는 것이다.
합성곱이 대표적이다. 같은 필터를 이미지의 모든 위치에 반복해서 적용하므로, 필터를 칩 안에 한 번 올려 두고 입력만 흘려보내면 옮긴 데이터 대비 계산량이 크게 늘어난다.
시스톨릭 배열은 그 흐름을 하드웨어로 굳힌 구조다. 데이터가 배열을 통과하는 동안 각 칸에서 곱셈과 덧셈이 일어나고, 중간 결과를 배열 안에서 이어받아 메모리 왕복을 줄인다.
여러 입력을 한꺼번에 처리하는 배치도 같은 가중치를 여러 번 재사용하게 만들어 같은 효과를 낸다.
정밀도를 낮추는 양자화 역시 같은 맥락이다. 값 하나를 표현하는 바이트 수가 줄면 같은 시간에 더 많은 값을 실어 나를 수 있으므로, 정확도만의 문제가 아니라 대역폭 문제이기도 하다.

정리하면 이렇다. 파이썬에서는 인터프리터가 명령을 해석하고 값을 꺼내 오는 과정이 병목이고,
네이티브 CPU에서는 읽어 오는 경로와 누적의 순서 의존성이 병목이며,
NPU에서는 계산기를 먹일 데이터를 옮기는 일과 가속기를 준비하는 고정 비용이 병목이다.
세 층위 모두 같은 뿌리에서 나온다. 이 과제의 MAC이 데이터를 재사용하지 않기 때문이다.
그리고 이것이 NPU의 성능 개선이 곱셈기를 더 넣는 쪽이 아니라 데이터를 어떻게 재사용하고 어떻게 덜 옮길지에 집중하는 이유다.

덧붙여 둘 것이 있다. 위 서술에서 이 프로젝트에서 직접 측정한 것은 파이썬 구현의 비용 분해뿐이다.
네이티브 CPU와 NPU에 대한 설명은 연산의 성질에서 따라 나오는 일반적인 해석이며, 이 과제에서 해당 하드웨어로 실측한 결과가 아니다.

## 11. 보너스 과제 (전부 구현)

### (1) 시뮬레이터 최적화 — 2D → 1D 평탄화
`Matrix.to_flat()` 로 N×N 을 길이 N² 1차원 리스트로 변환하고 `mac_1d()` 로 계산한다.
`bonus_compare_1d_2d()` 가 5×5·13×13·25×25에서 동일 입력·동일 반복(50회)으로 2D와 1D 시간을 비교 출력하며,
결과를 해석할 기준으로 이론 이득(1/N)과 평탄화 비용(`to_flat`)을 같은 표에 함께 보여 준다.
비교 전용 반복 횟수를 50회로 둔 것은 두 방식의 차이가 1/N 수준이라 기본 10회로는 측정 노이즈에 묻히기 때문이다.
(결과 해석은 위 "결과 리포트 · 상세 분석 4" 참조.)

### (2) 패턴 생성기
`generate_cross(N)`(가운데 행·열=1), `generate_x(N)`(두 대각선=1)로 임의 크기 Cross/X 패턴을 자동 생성한다.
재활용 지점은 두 곳이다.
- **성능 분석 표(3/5/13/25)** — 생성기로 각 크기의 패턴·필터를 만들어 시간을 측정한다.
- **모드1 입력** — 필터 입력 단계에서 `2`를 고르면 A=Cross·B=X 필터가, 패턴 입력 단계에서 `2`/`3`을 고르면
  Cross/X 패턴이 생성기로 채워진다(기본값 `1`은 기존대로 직접 입력). 생성된 행렬은 화면에 출력해 확인할 수 있다.
